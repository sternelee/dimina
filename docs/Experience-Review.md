# 项目维护经验

本文记录 Dimina 开发和排查中反复验证过的做法。开始修改框架、编译器或原生 SDK 前，应先确认问题所属层级、当前工作区状态和可执行的验证范围。

## 1. 在正确的层级修复问题

页面白屏、样式异常或按钮无响应只是表象。根因可能位于业务代码、编译产物、Service、Render、Native Bridge 或平台容器，不能根据出现问题的页面直接决定修改位置。

- 先沿源码、编译产物和消息链路定位根因，再选择修改层级。
- 业务侧临时改动可以用于验证推断，但框架问题最终要回到框架或 SDK 修复。
- 用户明确要求不改业务或示例代码时，不得把这些目录中的补丁作为最终方案。
- 一个页面恢复正常，不代表修复层级正确；还要检查相邻页面和共用链路。

## 2. 避免硬编码

固定路径、包名、字段、延时、高度和偏移通常只能解决单个用例。应优先从配置、运行时状态、平台能力或公开契约中取得这些值。

- UI 尺寸和位置使用布局、内容尺寸、safe area 或平台组件能力计算。
- 时序依赖使用明确的 ready、attached、消息确认或状态机表达。
- 文件和依赖路径从工程配置与构建产物解析，不绑定某台机器的目录。
- iOS 系统 framework 使用 `SDKROOT` 相对引用，例如 `System/Library/Frameworks/Foundation.framework`；不需要显式链接时直接移除，不能写死 `iPhoneOS<版本>.sdk`。
- 只为单一项目或页面增加特判前，要先证明它属于框架公开语义。

## 3. 以可验证的兼容语义为准

Dimina 的目标是复现小程序契约，不是根据 Vue、浏览器或某个平台的默认行为做近似实现。

- 小程序生命周期、observer、property、组件和 API 行为优先参考官方文档与可复现用例。
- Android、iOS、Harmony 和 Web 的实现不能凭名称推定一致，应分别检查容器与原生适配层。
- 开源库升级和协议变更先阅读上游迁移说明、规范与现有回归测试。
- 文档中的能力列表是已确认范围；未确认的行为应明确标注边界。

## 4. 不用延时掩盖时序问题

Service 与 Render 运行在不同线程或执行环境中，JavaScript 微任务不能保证跨线程顺序。`setTimeout`、连续 `nextTick` 或固定 animation frame 只能改变复现概率，不能建立可靠契约。

排查时应画清以下链路：

```text
事件产生 -> 监听注册 -> 消息发送 -> 消息消费 -> 渲染完成 -> 测量或回调
```

日志要同时覆盖 Service、Render 和容器，并携带 `bridgeId`、`moduleId`、页面路径及事件类型。修复后至少重复验证首次进入、再次进入、快速点击和展开/收起循环。

## 5. 验证相邻回归

构建成功、异常消失或 DOM 不为空，都不能代替最终行为验收。

- 框架修改至少验证原始复现、同链路组件和已有回归用例。
- UI 与渲染问题需要查看实际画面、DOM 或截图，检查遮挡、裁切、间距、safe area 和动画终态。
- 生命周期与状态问题要覆盖首次进入、返回后显示、销毁后重建和快速切换。
- 原生能力要区分编译、模拟器和真机结果；权限、驱动、签名与系统面板必须在目标设备验证。
- 无法运行的验证项要在交付说明中列出，不能用静态分析结果代替。

## 6. 控制诊断日志

诊断日志应有统一前缀、结构化字段和明确的时序位置。不要在高频路径铺设无关输出，也不要把临时日志留在最终实现中。修复完成后，保留必要的异常日志和可观测点，删除只为本次定位增加的内容。

## 7. 先读取当前工作区

仓库状态、当前分支和未提交改动可能随时变化。开始工作前至少检查：

- `git status`、当前分支、HEAD 和最近相关提交；
- 用户指定的源码、日志与编译产物；
- `node_modules`、`oh_modules` 或平台 SDK 中实际解析到的版本；
- 当前变更是否与已有未提交内容重叠。

遇到“之前正常、最近出现回归”时，优先比较相关提交和产物，而不是根据旧结论推测。除非用户明确要求，不回滚或覆盖已有改动。

## 8. 产品与交互约束

- 修复应保留现有视觉语言，包括按钮尺寸、圆角、标题栏、菜单和动画节奏。
- 不增加只服务于测试的入口，也不改变真实业务路径。
- 文案应明确、可本地化，并检查长文本、两行内容和不同语言下的布局。
- 连接、关闭、隐藏和失败状态要有清楚且不过量的反馈；快速重复错误不应叠加提示。
- 地图、导航、扫码、蓝牙、相机等能力先核对平台 SDK 的参数和限制，再决定上层适配方式。

## 9. 默认工作顺序

1. 读取当前状态、相关源码、产物、日志和权威参考。
2. 判断问题属于业务、编译器、Service、Render、SDK 还是平台容器。
3. 复现问题；无法运行时，用源码、产物和日志建立可检查的证据链。
4. 在正确层级做小范围修改，避免硬编码和延时补丁。
5. 验证原始问题、相邻路径、视觉状态和平台差异。
6. 删除临时日志，说明已验证内容、未验证内容和残余风险。

长任务应分阶段保存进展，避免上下文压缩或进程中断导致已确认结论丢失。
